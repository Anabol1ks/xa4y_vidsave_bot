## 1. Цели и границы

Нужно сделать привычный процесс скачивания видео красивее и информативнее **внутри чата Telegram**, без отдельного Mini App и без потери скорости текущего бота.

**В объёме работ:**

1. **Live Download Widget** — единый интерактивный визуальный шаблон скачивания для **YouTube Shorts, TikTok и Instagram Reels**.
2. **Analytics Widget** — приватная панель владельца с периодами **24 часа / 7 дней / 30 дней / всё время**.
3. **Error & Info States** — осмысленные состояния ошибок на **всех трёх платформах**, с безопасной информационной кнопкой **«Поддерживаемые форматы»**.
4. Сохранение текущих функций: обычная отправка видео, `file_id`-кэш, работа в группах, `/stats`, лимиты загрузок и защита данных.

**Не делаем:**

- `/me`, «Мои сохранения», пользовательские достижения и геймификацию;
- кнопку **«Попробовать снова» / Retry / Повторить** в любом виде, в том числе скрытый повторный запрос через widget API;
- автоматический ретрай по нажатию на виджет, обход авторизации платформ или просьбу предоставить cookies;
- отдельное веб-приложение / хостинг фронтенда только ради этих карточек;
- вымышленные проценты загрузки, фальшивые оценки времени и недостоверные статусы.

## 2. Зафиксированный визуальный стиль

Референс владельца — **чёрная минималистичная карточка** с крупной типографикой и ярким **голубым прогресс-баром** (на изображении: «YouTube Shorts», «Скачиваем видео…», крупное `68%`, «Этап 2 из 4»).

**Визуальные принципы:**

| Элемент | Решение |
| --- | --- |
| Контейнер | Почти чёрный фон, мягкая тонкая рамка, большое скругление, без объёмных теней |
| Основной текст | Белый, чёткий, крупный; шрифт клиента Telegram / системный, внешние шрифты не загружаем |
| Вторичный текст | Спокойный серый |
| Основной акцент | Голубая горизонтальная полоса прогресса, единая для всех платформ |
| Платформа | Логотип и название в верхней строке: YouTube Shorts / TikTok / Instagram Reels |
| Логотипы | Компактные встроенные SVG либо чистые стилизованные значки без внешних изображений |
| Статус | Крупная цифра **только там, где есть измеренный процент**; иначе понятный текст + ненавязчивая индикация ожидания |
| Этапы | Подпись «Этап N из 4» и аккуратные статусы / индикаторы в нижней области |
| Анимация | Плавная, сдержанная; без мерцания, агрессивного свечения и постоянно вращающихся декоративных элементов |
| Адаптивность | Ширина пузыря Telegram ~320–430 px на телефоне; поддержка узкой ширины от 200 px и увеличенного текста |
| Темы | В обоих режимах Telegram сохраняем **согласованный чёрный фирменный дизайн**, проверяем контраст и читаемость; не требуем принудительно тёмную тему Telegram |

**Ориентировочные токены для прототипа, не жёсткий контракт:** фон `#050505`, рамка `#292929`, основной текст `#FFFFFF`, вторичный `#A8A8A8`, полоса `#2696EA`, трек `#303030`, успех `#16C784`, ошибка `#F36C6C`. Финальные оттенки — после проверки в настоящем Telegram на мобильном и desktop.

**Важное:** на приложенном референсе **голубой** — акцент полосы, **красный** — только знак YouTube. Не превращать три платформы в три совершенно разных карточки.

**Скелет загрузочной карточки:**

```text
╭─────────────────────────────────╮
│ [значок] YouTube Shorts  Загрузка│
│                                 │
│ Скачиваем видео…                │
│ 68%                             │
│ █████████████░░░░░░             │
│                                 │
│ Этап 2 из 4 · Загрузка          │
│ ✓ Ссылка проверена  ◉ Загрузка  │
╰─────────────────────────────────╯
```

Тексты должны помещаться на телефоне: при дефиците ширины правая подпись переносится/сокращается без обрезания процента и кнопок. Скриншот — **визуальный ориентир**, а не требование пиксельного совпадения с не-виджетовым рендером.

## 3. Live Download Widget: сценарий и состояния

### 3.1 Три платформы — один компонент

- **YouTube Shorts:** логотип YouTube, подпись `YouTube Shorts`.
- **TikTok:** логотип TikTok, подпись `TikTok`.
- **Instagram Reels:** логотип Instagram, подпись `Instagram Reels`.
- Во всём остальном общая композиция, полоска прогресса, типографика, анимация, обработка ошибок.
- Обрабатываются **только поддерживаемые ссылки** текущего парсера; поддержка новых форматов не входит в этапы 1–4.

### 3.2 Единый жизненный цикл

| № | Состояние | Текст | Индикация и условие завершения |
| --- | --- | --- | --- |
| 1 | `validating` | «Проверяем ссылку…» | Без вымышленного процента. Переход при успешном разборе и проверке допустимости. |
| 2 | `downloading` | «Скачиваем видео…» | **Измеренный прогресс скачивания** из yt-dlp, если источник выдаёт объём и процент. Если данных нет — неопределённая анимация, не `68%` «с потолка». |
| 3 | `preparing` | «Подготавливаем файл…» | Неопределённая индикация для слияния/проверки, либо быстрый пропуск этапа без искусственной задержки. |
| 4 | `sending` | «Отправляем в Telegram…» | Неопределённая индикация, **не выдавать загрузку в Telegram за известный процент**, пока он технически не измеряется. |
| — | `success` | «Готово! Видео отправлено» | Можно показать `100%`, **только после подтверждения Telegram Bot API**. Видео остаётся обычным Telegram-видеосообщением. |
| — | `failed` | «Не удалось скачать видео» или уточнённый текст | Спокойный красный статус, ясная причина/подсказка, **без Retry**. |

Пример этапа 2 и внешний вид должны соответствовать референсу: «Скачиваем видео…», большая цифра измеренного процента, голубая полоса, «Этап 2 из 4 · Загрузка», два минималистичных состояния внизу.

### 3.3 Специальные переходы

- **Попадание в кэш `file_id`:** не запускать yt-dlp; отправить видео без искусственных этапов. Предпочтительный UX — **мгновенная отправка без дополнительной карточки**, чтобы не плодить сообщения. При необходимости можно показать короткое состояние «Из кэша», но только если это не замедляет результат.
- **Dedup по SHA-256:** после локальной обработки допускается быстрое состояние «Уже есть в кэше» перед отправкой.
- **Быстрая операция:** не задерживать успешную отправку ради отображения анимации.
- **Ошибка/тайм-аут:** состояние становится терминальным; UI сам по себе не запускает скачивание заново.
- **Успешная отправка:** видео отправлено отдельно. Предлагаемое поведение — кратко показать `success`, затем удалить служебный виджет (например, через 5–10 секунд), чтобы чат не засорялся. Это **настройка UX, уточняемая на реальном прототипе**; удалять само видео нельзя.
- **Ошибки:** оставить информационную карточку или обычный текст с причиной, пока пользователь не увидит сообщение; не создавать бесконечный поток уведомлений.

### 3.4 Источник достоверного прогресса

Сейчас `internal/download/download.go` исполняет yt-dlp и буферизует stdout/stderr до завершения. На этапе 3 потребуется:

1. Ввести `ProgressEvent` и callback/канал прогресса по одной конкретной задаче.
2. Потоково считывать progress-вывод yt-dlp, нормализовать формат (полученные байты / известный размер, с учётом фрагментов и отдельно скачиваемых дорожек).
3. Для YouTube, где могут загружаться отдельно видео и аудио, **не обещать общую линейную готовность**, если нет надёжного суммарного объёма. Допустима подпись «Загрузка видео» и состояние «Объединение дорожек».
4. Ограничить частоту обновлений виджета: агрегировать события, передавать заметные изменения и переходы; целевой ориентир **не чаще 1 раза в 2–3 секунды на активную загрузку** (адаптировать при rate limits).
5. После ошибки update виджета **не останавливать скачивание**, а продолжить обычный путь отправки и безопасный fallback.

## 4. Ошибки и безопасные действия — все три платформы

Единая схема для YouTube Shorts, TikTok и Instagram Reels. Тексты уточняются по фактическому типу ошибки, а не угадываются по одной платформе.

| Тип | Видимый текст | Подсказка |
| --- | --- | --- |
| `unsupported_url` | «Ссылка не поддерживается» | «Проверь, что это прямая ссылка на поддерживаемое видео» |
| `auth_required` / `private_video` | «Видео недоступно» | «Возможно, нужен вход в аккаунт или видео закрыто» |
| `source_restricted` / `source_rate_limited` | «Платформа временно ограничила доступ» | «Можно отправить другую публичную ссылку позже» |
| `download_error` / `network_error` | «Не удалось скачать видео» | «Возникла временная ошибка при получении файла» |
| `too_large` | «Видео слишком большое» | «Лимит отправки этим ботом — 50 МиБ» |
| `too_long` | «Видео слишком длинное» | Уточнять лимит только там, где он реально существует (сейчас YouTube Shorts — 180 секунд) |
| `send_error` | «Не удалось отправить видео в Telegram» | «Попробуй отправить другую ссылку позже» |
| `busy` / `limit_reached` | «Слишком много запросов» | «Дождись завершения текущей загрузки» |

**Разрешённое действие в карточке:** кнопка/раскрываемая секция **«Поддерживаемые форматы»**. Она только показывает краткий список поддерживаемых форматов и примеры URL; предпочтительно реализуется **локально в HTML без запроса к боту**.

**Запрещённые действия:** `retry`, `redownload`, `start-download`, автоматическая отправка исходного URL через `TelegramWidget.request()`, массовое создание задач, «повторить всё». Никакого скрытого аналога этих кнопок.

**Дружелюбный текст, а не интерактив:** «При необходимости отправь новую ссылку в чат». Пользователь инициирует новую операцию только **новым сообщением**, под серверными лимитами.

## 5. Ограничение спама и нагрузки

Отсутствие кнопки Retry — обязательное продуктовое решение, но **само по себе оно не заменяет server-side rate limiting**. На этапе 3 спроектировать и проверить:

- Лимиты на пользователя и, при работе в группе, на чат; значения должны быть конфигурируемыми, а не зашитыми в widget JS.
- Максимум **одна выполняющаяся загрузка на пользователя** как исходный ориентир, с защитой от повторной постановки идентичного `userID + sourceKey` во время выполнения.
- Существующий глобальный `MAX_CONCURRENT_DOWNLOADS` сохранить (сейчас по умолчанию 3). Отдельно ограничить количество **ожидающих** задач, не создавать неограниченную очередь.
- Краткий cooldown на повторные идентичные запросы, включая запрос после ошибки. Конкретные значения и UX-ответ проверить по нагрузочным сценариям перед этапом 3.
- Telegram `429` / `retry_after`, лимиты обновления виджетов и yt-dlp внутренние network retries учитывать отдельно. Технические повторы yt-dlp **не должны создавать новые пользовательские задания**.
- Никаких секретных токенов, cookie, исходных ссылок с приватными параметрами и персональных данных в widget state.
- Статистика запросов должна учитывать пользовательское событие один раз, а не каждый progress update.

## 6. Analytics Widget (`/stats`) — только для владельца

### 6.1 Доступ

- Использовать существующий список `ADMIN_TELEGRAM_IDS` (владелец уже настроил доступ через свой аккаунт).
- Авторизацию проверять **на backend по Telegram `from.id`**, отдельно для каждой команды и каждого интерактивного запроса `widget_query`, только для private chat.
- Не полагаться на видимость команды в меню, client-side скрытие кнопок или переданный через widget идентификатор.
- Предпочтительно **не shared widget**; состояние приватной аналитики привязано к конкретному владельцу и сообщению; не отправлять приватные данные в общие каналы/группы.
- Текущий текстовый `/stats` сохранить как **fallback** на случай сбоя/недоступности виджетов; существующий read-only просмотр статистики с VPS не менять.

### 6.2 Периоды и смысл метрик

| Период | Временное окно | Основной показатель «Пользователи» |
| --- | --- | --- |
| `24h` | Последние 24 часа до текущего момента | Уникальные активные пользователи за 24 ч |
| `7d` | Последние 7 × 24 часа | Уникальные активные пользователи за 7 дней (WAU) |
| `30d` | Последние 30 × 24 часов | Уникальные активные пользователи за 30 дней (MAU) |
| `all` | С момента **фактического начала новой аналитики** | Все уникальные учтённые пользователи |

Во **всех** периодах показываем:

- **Пользователи** (уникальные активные в окне / total в `all`), и отдельно **новые** за период, если места хватает;
- **Запросы**;
- **Успешно отправлено**;
- **Ошибки** и **процент успешности**;
- **Cache hits** — по реально завершившимся обращениям к `file_id` / дедупликации;
- **Разбивка по платформам**: TikTok, Instagram Reels, YouTube Shorts;
- **Распределение ошибок** по кодам (при наличии ошибок);
- **Небольшой график активности**: для 24h — по часам; для 7d/30d — по дням; для `all` — по месяцам или с динамическим шагом.

**Уточнение решения (11.11.2026):** показатель «Видео» должен охватывать **всю историю**, а не только время после внедрения аналитики пользователей. Источник — историческая `media_cache`: по `created_at` считаем новые уникальные ссылки за 24ч/7д/30д, а в `all` — все сохранённые ссылки, включая февраль—октябрь 2026. Столбики по платформам и график «Видео» тоже охватывают старые месяцы. Эти величины **не** эквивалентны количеству запросов, скачиваний, пересылок или отдельных файлов по SHA256. Запросы, успешные отправки, ошибки и пользователи остаются с момента включения новой аналитики, и эти две серии нельзя складывать.

### 6.3 Дизайн аналитики

- Тот же чёрный фирменный контейнер и типографика, что у загрузки.
- Заголовок `XA4Y · Analytics` и горизонтальный переключатель `24ч | 7д | 30д | Всё`.
- Главные показатели крупными числами, 2×2 или компактная сетка для узкого экрана.
- Ниже — тонкий линейный/столбиковый график в голубом акценте, отдельная компактная легенда и платформы.
- Если нет данных: `Пока нет событий за этот период` — без «0% успешности», когда запросов 0.
- Для длинных периодов данные агрегируются на Go/backend, **не загружаем сырые события или user IDs внутрь виджета**.
- Кнопки периода не создают скачивания; `TelegramWidget.request()` может запросить только разрешённый агрегат. Ответ/состояние обновляется без нового сообщения.
- Если всё не помещается в высоту 600 px — упрощаем количество строк, не делаем прокручиваемую мини-страницу; при необходимости разделяем обзор и детали, не нарушая стиль.

## 7. Telegram Widgets: подтверждённые технические ограничения

Сверено с официальными документами 11.11.2026: [Telegram Widgets](https://core.telegram.org/bots/widgets), [Telegram Bot API](https://core.telegram.org/bots/api), [Changelog](https://core.telegram.org/bots/api-changelog).

- Telegram Bot API **10.4 (09.11.2026)**: `sendWidget`, `editMessageWidgetData`, `answerWidgetQuery`, `widget_query`.
- **Production:** виджеты можно отправлять **только в личный чат** бота; в группах и inline-режиме пока оставить старый текстовый/видео UX. Новые клиенты поддерживают виджеты; старые могут показывать unsupported media и caption.
- Widget — **не WebView**, исполняется в QuickJS sandbox. Нет HTTP, WebSocket, внешних библиотек, внешних шрифтов и изображений, обычного браузерного DOM/API. Изображения/иконки — встроенные SVG/data URLs.
- HTML ограничен **32 768 байт UTF-8** и **4 096 байт после zlib level 9**. Код фиксируется при отправке; меняются только данные.
- `chat_data` и `public_data` — **не более 1 024 байт** каждое. На каждый progress update отдаём только короткое состояние (`stage`, `progress`, `platform`, `error_code`, `rev`).
- Запросы виджета к боту — **1–64 байта**; ответ бота — до 1024 байт, **ответить не позже 15 секунд**.
- Лимит запросов: **5 на 5 секунд на пользователя и бота**, включая background. В личном чате фоновые запросы возможны не чаще примерно **одного в 5 секунд**, пока виджет виден. Не делать частые polling-вызовы от виджета для прогресса, предпочитать `editMessageWidgetData` с серверной стороны.
- `editMessageWidgetData` учитывается в лимитах отправки сообщений бота; обновления нужно **coalesce / throttle**. Изменения только при смене состояния и значимом росте прогресса.
- Габариты: пузырь примерно **200–600 px шириной**, контент **50–600 px высотой**; прокрутки внутри виджета нет.
- Состояние виджета обновлять с монотонной `rev` для защиты от устаревших событий, не давать UI «откатываться» назад.
- Для новых событий в Go понадобится адаптер к новому Bot API; текущая зависимость `github.com/go-telegram-bot-api/telegram-bot-api/v5 v5.5.1` предшествует поддержке Widgets. Выбор: официальный upgrade, если версия с API уже доступна, либо **тонкий собственный адаптер** на `net/http` и расширение модели входящих Update; не ломать существующий polling, команды и inline.

## 8. Архитектурные контракты будущей реализации

**Widget state, пример (не окончательная схема):**

```json
{"v":1,"r":18,"platform":"youtube","stage":"downloading","progress":68}
```

- `v` — версия формата; `r` — монотонная ревизия; `platform` ∈ `youtube`, `tiktok`, `instagram`.
- `stage` ∈ `validating`, `downloading`, `preparing`, `sending`, `success`, `failed`.
- `progress` — **только измеренный** процент скачивания в пределах 0–100, поле **отсутствует**, если неизвестен.
- `error_code` / краткая подсказка — только из белого списка; не отдавать stderr yt-dlp или внутренние URL.
- Истина о статусе работы и правах доступа — только на сервере. HTML доверять нельзя.
- Для аналитики нужны агрегированные запросы PostgreSQL по временному окну, платформе, успешности, ошибкам и временным корзинам. Индексы и нагрузку на БД проверить на этапе 2.
- При любой ошибке Widget API скачивание и отправка обычного видео должны оставаться работоспособными.

## 10. Общие критерии приёмки и безопасность релиза

- **По умолчанию** никаких действий из виджета, инициирующих новое скачивание. Кнопка Retry отсутствует в коде и в интерфейсе.
- Не нарушены текущие YouTube, TikTok, Instagram, отправка Telegram-видео, `file_id`-кэш и группы.
- `/stats` и analytics widget доступны исключительно `ADMIN_TELEGRAM_IDS`, только в личном чате; все widget queries проверяются сервером.
- Progress соответствует реальным измерениям; неизвестный процент отображается как «в процессе», а не фиксированная цифра.
- Аккуратный fallback при неподдерживаемом клиенте / ошибке Bot API: caption или обычный текст, **видео всё равно отправляется**.
- UI соответствует приложенному владельцем чёрному референсу и читается в мобильном Telegram, Telegram Desktop, при увеличенном тексте.
- Автотесты: валидные/невалидные состояния, авторизация, тайминги/лимиты запросов, переходы состояния, дедупликация, корректность аналитики; регрессионный `go test ./...`, `go vet ./...`, Docker build.
- Никаких прямых изменений production БД без обратимо протестированной миграции; никакого публичного endpoint с приватной аналитикой.
- Разработка в **отдельной feature-ветке**, PR, зелёный CI, затем merge и автоматический deploy; изменения исходного кода только после этапа 1.

## 11. Открытые детали (не блокируют фиксацию этапа 1)

1. Точный интервал удаления успешной служебной карточки и нужно ли вообще оставлять `success` на экране.
2. Финальные размеры и отступы после просмотра **реального** Telegram-виджета, а не картинки-макета.
3. Конкретные per-user/per-chat лимиты и cooldown — определить на этапе 3 после измерения нагрузки, сохранив запрет кнопки Retry.
4. Возможности фактического `%` для каждого типа формата/нескольких потоков yt-dlp; не измеряется — не показываем.
5. Способ интеграции нового `widget_query` со старой Go-библиотекой без конкурирующего polling.
