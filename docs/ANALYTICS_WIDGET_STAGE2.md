# Telegram Analytics Widget · Stage 2

**Спецификация:** [WIDGETS_SPEC_V1.md](WIDGETS_SPEC_V1.md) · **Статус:** реализация в PR, production-переключатель **выключен по умолчанию**.

## Возможности

- `/stats` в личном чате владельца отправляет один HTML Widget с визуальным стилем XA4Y: тёмная карточка, крупные числа, голубые акценты, небольшой график и компактные доли Instagram Reels / TikTok / YouTube Shorts.
- Периоды: **24ч / 7д / 30д / Всё**, без создания новых сообщений при переключении.
- Пользователи (активные уникальные за период, для «Всё» — все учтённые), новые пользователи, запросы, успешные отправки, ошибки, процент успешности, попадания в кэш, распределение по платформам и топ причин ошибок.
- Точки графика показывают **количество реальных запросов** за части выбранного интервала, не оценку. Для 24ч — 12 отрезков по 2 часа; 7д — 7 отрезков по 24 часа; 30д — 10 отрезков по 3 дня; «Всё» — 12 равных частей с даты первого учтённого запроса.
- Только в «Всё» — отдельное число уникальных ссылок в `media_cache` **за всю историю**, включая период до трекинга пользователей; нельзя суммировать его с новыми запросами.
- Если за период нет запросов, процент успеха отображается как **—**, а не как 0%.

## Доступ и приватность

- `/stats` и `/stats_text` разрешены только при точном совпадении `message.from.id` с `ADMIN_TELEGRAM_IDS`, **только в личном чате**.
- Каждый `widget_query` проверяет `from.id`, `chat.id`, `chat.type=private`, тип запроса `data`, allowlist и допустимость ровно одного из четырёх периодов.
- Запросы виджета **не** могут инициировать скачивания, ретраи, работу с URL или изменения данных в БД.
- В `chat_data` и ответах содержатся **только агрегаты**; нет Telegram ID, имён, ссылок, паролей и отдельных событий. `public_data` и `is_shared` не используются.
- Существующий локальный интерфейс статистики на `127.0.0.1:18873` и кэш видео не изменяются.

## Интеграция Telegram API 10.4

Зависимость `go-telegram-bot-api/v5 v5.5.1` не распознаёт новый тип `widget_query`. Вместо второго вызова `getUpdates` разработан **единый polling** с JSON-декодированием старых `message` / `inline_query` и новых `widget_query` в одном потоке. Когда feature flag отключён, используется старый polling без изменений.

Отправка виджета: `sendWidget`; ответы на нажатия: `answerWidgetQuery` (не позднее 15 сек); сохранение нового периода: `editMessageWidgetData`. HTML встроен непосредственно в Go-бинарник через `go:embed`.

Ограничения: HTML не больше 32 768 байт, сжатый zlib level 9 не больше 4096 байт, `chat_data` и ответы не больше 1024 байт, запрос не больше 64 байт; частота Telegram — не больше 5 запросов на пользователя за 5 секунд. Веб-сетевых запросов в виджете нет.

## Feature flag и fallback

```env
ANALYTICS_WIDGET_ENABLED=false
```

- По умолчанию **false**: `/stats` продолжает отправлять **текстовый** отчёт и использует старый polling; существующее поведение не затронуто.
- После проверки отдельного тестового бота (с **отдельным** BOT_TOKEN) включить **true** на staging, затем на production после одобрения. Не запускать второй экземпляр с тем же Telegram BOT_TOKEN, так как polling конкурирует.
- Если `sendWidget` вернул ошибку, `/stats` автоматически отправляет текущий текстовый отчёт.
- Для старых клиентов в виджете есть caption с рекомендацией `/stats_text`. Эта команда всегда даёт обычный текстовый отчёт независимо от feature flag.
- При сбоях отдельных запросов виджета сохранённое состояние не теряется: Telegram клиента видит последнюю успешную выборку. Периоды не вызывают повторную загрузку видео.

## Перед релизом

- `go test ./...`, `go vet ./...`, `go test -race ./...`, `go build ./...`.
- CI: интеграционные тесты PostgreSQL на **одноразовой тестовой БД**; проверка SQL-окон 24ч/7д/30д/всё, нулевых запросов, графиков, безопасности, HTML-запретов и wire-адаптера.
- E2E в Telegram нужно выполнить **после** CI на тестовом аккаунте/боте без прав на production токен, затем на владельце `/stats`. Проверить iOS/Android/Desktop, светлую и тёмную темы и старый клиент с fallback.
- Не объединять PR без зелёного CI. Изменение `main` запускает автоматический production Docker-deploy, поэтому только явное одобрение и staged rollout.

**Не входит в Stage 2:** виджеты загрузки, кнопки Retry, My Saves, автоматическое скачивание из действий виджета. Это следующие этапы из [спецификации](WIDGETS_SPEC_V1.md).
