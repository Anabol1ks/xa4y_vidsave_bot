# XA4Y VideoSave — Stage 3: Live Download Widget

Базовая спецификация: [WIDGETS_SPEC_V1.md](WIDGETS_SPEC_V1.md). Этот документ описывает реализацию Stage 3 — **без включения в production до E2E в Telegram**.

## Сценарий пользователя

- Поддерживаются ровно существующие три платформы: **YouTube Shorts**, **TikTok**, **Instagram Reels**.
- Бот принимает ссылку по-старому. Сначала проверяет PostgreSQL-кэш по `source_key`. Если `file_id` уже есть, **сразу отправляет видео**, без виджета и запуска yt-dlp.
- Для нового видео в личном чате отправляется защищённый HTML Widget с тёмным фоном, большими цифрами, голубым progress bar, лаконичными текстами и идентификатором платформы. Высота/ширина адаптивны.
- Четыре состояния: `validating` («Проверяем ссылку»), `downloading` («Скачиваем видео»), `preparing` («Подготавливаем файл»), `sending` («Отправляем в Telegram»). После успешного API-ответа `success` и **100%**, затем через 6 секунд удаляется **только служебный виджет**, а не видео.
- **Процент в `downloading` — текущий поток yt-dlp**, рассчитанный только из реально полученных `downloaded_bytes / total_bytes`. Если total неизвестен, остаётся честная неопределённая анимация («···»). `total_bytes_estimate` не преобразуется в фиктивный процент. Для YouTube видео/аудио могут передаваться отдельными потоками, процент относится только к текущему потоку, **не к готовности всей операции**.
- Для `preparing` и `sending` процентов нет: прогресс Telegram upload не измеряется. Быстрые стадии могут не показаться из-за throttle, намеренно **не задерживаем видео ради анимации**.
- Если Telegram отверг `sendWidget`, используется прежнее сообщение «⏳ сек, качаю». Ошибки загрузки и отправки пока показываются **старым текстовым сообщением**, виджет удаляется. Отдельные интерактивные error-card состояния — **этап 4**.
- В группах и inline-режиме сохраняется обычный UX. HTML Widget отправляется только в личный чат.
- **Нет Retry, callbacks, запросов от виджета, скрытых загрузок.** В Stage 4 только локальная справка «Поддерживаемые форматы».

## Настройки и безопасный rollout

В `.env.example` добавлены переменные, по умолчанию функция **выключена**:

```dotenv
DOWNLOAD_WIDGET_ENABLED=false
DOWNLOAD_WIDGET_PILOT_IDS=
MAX_WAITING_DOWNLOADS=6
DOWNLOAD_QUEUE_TIMEOUT_SEC=20
DOWNLOAD_TIMEOUT_SEC=240
DOWNLOAD_USER_COOLDOWN_SEC=3
DOWNLOAD_SOURCE_COOLDOWN_SEC=30
DOWNLOAD_GROUP_PER_MINUTE=20
```

Для **первой проверки на владельце**, не затрагивая обычных пользователей:

```dotenv
DOWNLOAD_WIDGET_ENABLED=true
DOWNLOAD_WIDGET_PILOT_IDS=665731091
```

Пустой `DOWNLOAD_WIDGET_PILOT_IDS` при `DOWNLOAD_WIDGET_ENABLED=true` означает **все пользователи**: запрещено включать так до проверки.

Если флаг выключен или пользователь не в пилоте — текущие `DownloadVideo`, `⏳ сек, качаю`, cache hit, группа, Telegram send и analytics ведут себя как раньше. `ANALYTICS_WIDGET_ENABLED` независим и не меняется.

**Откат:** вернуть `DOWNLOAD_WIDGET_ENABLED=false` и штатно пересоздать только bot-контейнер, сохранив PostgreSQL. Никогда не запускать второй экземпляр с тем же `BOT_TOKEN` (конкурирующие polling).

## Серверная защита

В пилоте действуют:
- Один активный запрос на Telegram user ID (в любой чат), не только один yt-dlp. Дубли отклоняются до cache lookup и создания виджета.
- Cooldown **3 секунды после завершения запроса** для пользователя и **30 секунд** для повторной той же ссылки.
- В группах — **20 разрешённых запросов в минуту на чат**, плюс индивидуальные лимиты.
- Глобальная ёмкость из `MAX_CONCURRENT_DOWNLOADS` (по умолчанию 3) исполнителей + `MAX_WAITING_DOWNLOADS` (по умолчанию 6) ожидающих, максимум 20 секунд ожидания. **Место резервируется до отправки Widget**, поэтому переполнение не создаёт пачку статусных карточек. Дополнительные запросы получают информативный отказ, причём ответы `busy` ограничены до одного сообщения на чат за 10 секунд.
- Ограничение активного процесса yt-dlp — 240 секунд через `exec.CommandContext`. Внутренние yt-dlp retries не создают новые задачи.
- При перегрузке никакого автоматического повтора. Уже имеющиеся file_id-кэши продолжают работать максимально быстро, но лимит на пользователя защищает от повторной массовой отправки.

## Техническое устройство

- `internal/download/progress.go`: потоковая обработка строк yt-dlp из **stdout и stderr**, маркер `VIDSAVE_PROGRESS|`, нулевые/отсутствующие размеры, отсутствие фальшивого процента; диагностика каждого потока ограничена 64 КиБ. На реальном yt-dlp 2026.08.19 с локальным HTTP-файлом подтверждено: прогресс с `--print after_move:filepath` шёл именно в **stdout**. Обработчик отделяет строки прогресса от пути конечного файла и проверяет, что он лежит во временной директории.
- При наличии callback включаем `--progress`, `--newline`, `--no-color`, `--progress-template`. В старом режиме аргументы yt-dlp **не меняются**. `--progress` явно нужен, так как существующий `--print after_move:filepath` подразумевает тихий режим.
- `internal/bot/download_widget.html`: автономный QuickJS HTML/CSS/SVG, без внешних ассетов и запросов, 7363 байта HTML / около 3.2 КиБ zlib9 (проверяется автоматически).
- `internal/bot/download_widget_api.go`: отдельный HTTP-клиент с 8-секундным тайм-аутом для `sendWidget`/`editMessageWidgetData`. Не меняет существующий клиент отправки больших видео. Токен не выводится при транспортных ошибках.
- `internal/bot/download_widget_session.go`: callback не блокируется сетью; сохраняется последнее событие, изменения сериализуются и coalesce/throttle до ~3 секунд; терминальный статус синхронизируется отдельно, виджет удаляется после успешной отправки видео.
- `internal/bot/download_guard.go`: ограниченная очередь, cooldown, очистка старых ключей.
- JSON widget state передаёт только `v,p,s,n,r` (версия, платформа, стадия, процент текущего потока/NULL, ревизия), существенно меньше 1024 байт. **Нет исходных ссылок, персональных данных, названий роликов, секрета бота, cookies.**
- На старых Telegram-клиентах виджет может отображаться неподдерживаемым медиа, но штатная отправка видео не зависит от виджета. Для строгой совместимости рекомендуется включать функцию в пилоте, собирать обратную связь и только затем расширять.

## Проверки перед разрешением merge и rollout

1. `go test -count=1 ./...`, `go test -race ./...`, `go vet ./...`, `go build ./...`.
2. GitHub Actions с Docker-билдом; PostgreSQL интеграционный тест на disposable DB, локальный fake Telegram API и mock yt-dlp.
3. В личном чате владельца по одной **новой публичной ссылке** с каждой из трёх платформ: появление карточки, реальный прогресс или «···», отдельное видео, короткий success, удаление карточки.
4. Проверить **кэш-хит** (видео приходит сразу без карточки), большой/закрытый ролик, отказ Telegram Widget API (fallback), несколько одновременных запросов, cooldown, очереди и тайм-аут.
5. Проверить группы, inline, `/stats`, `/stats_text` и read-only `127.0.0.1:18873/stats` на отсутствие регрессии.
6. Производственный флаг включается только после явного решения; сначала `DOWNLOAD_WIDGET_PILOT_IDS=665731091`, не все пользователи.

**Ограничение:** на текущем этапе Mock/CI-тесты **не** доказывают визуальную работоспособность в реальном Telegram-клиенте. E2E с участием владельца — отдельный релизный gate.
